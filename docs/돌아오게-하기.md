# 왜 안 늘었나 · 무엇을 고쳤나

2026-09-02. 홍보를 늘리고 앱을 여러 번 고쳤는데도 이용자가 안 늘었다.
짐작으로 또 고치지 않으려고 먼저 숫자를 봤다.

## 1. 숫자

| | |
|---|---|
| 미니앱에 온 사람 | **43명** |
| 한 번 켜고 다시 안 온 사람 | **29명 (67%)** |
| 온 그날 하루만 쓴 사람 | **38명 (88%)** |
| 다른 날 또 온 사람 | 5명 |
| 로그인 30번 한 사람 | 1명 — 사장님이다 |
| 콘텐츠를 쓴 횟수 | 87번 = 한 사람당 2번 |
| 가장 많이 쓰인 것(타로)을 써 본 사람 | **7명** |
| 알림을 켠 사람 | **1명** |
| 도장을 가진 사람 | **1명** |

날마다 새로 온 사람: 8/26 **8명**, 8/27 5, 8/28 3, 8/29 3, 8/30 **8명**, 8/31 2, 9/1 1.

**사람은 왔다.** 홍보한 날은 여덟 명씩 왔다. 그 여덟이 한 명도 안 남았을 뿐이다.

## 2. 진단

**쌓이는 층이 없으니 「오늘 이용자」가 곧 「오늘 새로 온 사람」이다.**
홍보하면 그날 8명, 안 하면 1명, 다음 날은 다시 0에서 시작한다. 홍보를 두 배로
해도 그날 16명이고 이틀 뒤엔 똑같이 0이다. [홍보.md](홍보.md) 첫 줄이 이미
그렇게 적어 두었다 — *"커뮤니티 글은 올린 날 하루 트래픽이고, 이틀이면 0으로
돌아온다."*

### 뿌리 — 값을 거꾸로 매기고 있었다

| | 값 | 내일 또 볼 이유 |
|---|---|---|
| 내 사주 풀이 | **공짜** | **없다.** 사주는 안 바뀐다. 한 번 읽으면 끝 |
| 오늘 어때요 | **1엽전** | 있다. 날마다 바뀐다 |

**공짜로 주던 것은 평생 안 바뀌는 것이고, 날마다 바뀌는 것에는 돈을 받았다.**
가입 엽전 3개를 쓰고 나면 내일 열 이유가 없다. 67%가 한 번 켜고 안 오는 게
이것 하나로 설명된다.

게다가 그 순위는 **웹 `/tti` 에서 이미 공짜로 풀고 있고**, 날마다 인스타와 X 에도
그림으로 올린다. 밖에서는 공짜인 것을 앱 안에서만 돈을 받고 있었다.

### 기능을 더 만드는 것은 답이 아니었다

27개 중 가장 많이 쓰인 것이 7명이다. 하나 더 만들면 43명이 27개 대신 28개를
나눠 갖는다.

## 3. 고친 것

### ① 날마다 바뀌는 것을 공짜로, 첫 화면에

새 길 `POST /api/tti-today` — **엽전을 쓰지 않고** 순위 열두 줄과 내 띠가 몇
위인지를 준다. 홈 히어로가 "오늘은 어떤 기운일까요" 라고 묻고 바로 밑에서 답한다
(전에는 묻기만 하고 답은 1엽전이었다).

나누는 자리를 **돈이 드는가**로 다시 그었다.

    공짜   순위 · 내 등수 · 왜(삼합·육합·충·형)   computeTtiRanking() 은 계산이라 안 든다
    1엽전  오늘을 어떻게 보내면 좋은지            Gemini 를 부르므로 돈이 나간다

⚠️ **파는 것을 깎은 게 아니다.** 밖에서 공짜인 것을 안에서도 공짜로 맞췄고,
만드는 데 돈이 드는 쪽은 그대로 받는다.

지킴이: [test/tti-today-free.test.mjs](../test/tti-today-free.test.mjs)

### ② 도장을 첫 화면으로, 누르지 않아도 찍히게

전에는 **홈 → 메뉴 → 무료 엽전 받기 → 출석 도장** 으로 세 단계 안쪽이었다.
한 번 켜고 마는 사람은 거기까지 못 간다(그래서 43명 중 1명이었다).

이제 앱을 켜면 저절로 찍히고, 홈에 「3일째 오시는 중 · 개근까지 4일」이 보인다.
**다시 온 사람에게 또 일을 시키면 거기서 또 샌다.**

7일 보상은 여전히 서로 다른 이레가 필요하다 — id 가 날짜라 하루에 두 번은
안 찍힌다.

지킴이: [test/checkin-on-open.test.mjs](../test/checkin-on-open.test.mjs)

### ③ 알림 — 도장이 찍힌 뒤에 묻는다

토스 SDK 에 `Notification.requestAgreement` 가 있는데 한 줄도 안 쓰고 있었다.

⚠️ **언제 묻는지가 이 기능의 전부다.** 처음 온 사람에게 물으면 대개 거절이고
거절은 되돌리기 어렵다. 그래서 **이틀째부터** 묻는다 — 다시 왔다는 것은 이미
좋았다는 뜻이라, 그때가 유일하게 예라고 할 만한 순간이다. 한 번만 묻는다.

⚠️ **아직 안 켜진다.** `mini/src/main.js` 의 `NOTIFY_TEMPLATE` 이 비어 있다.
앱인토스 콘솔 → 스마트발송에서 템플릿을 만들고 그 코드를 넣어야 묻기 시작한다.
비어 있으면 아예 안 묻는다 — 코드 없이 부르면 열리다 마는 창을 보여 주고
그 사람의 한 번뿐인 기회를 버린다.

### ④ 왜 안 돌아오는지 물어보기

⚠️ **①~③ 은 「좋았는데 잊은 사람」을 되부르는 장치다.** 애초에 안 좋았던
거라면 알림은 차단만 부른다. 그 둘을 가르려면 물어봐야 하는데, **미니앱에는
묻는 자리 자체가 없었다**(`reading_feedback` 0건은 아무도 안 눌러서가 아니다).

풀이 끝에 「이 풀이가 도움이 되셨나요 · 그렇다 / 아니다」 한 줄을 넣었다.
새 표 `mini_feedback`, 새 길 `POST /mini/api/feedback`.

- 별 다섯 개 같은 것을 안 쓴다. 둘 중 하나면 누르지만 고르게 하면 안 누른다
- 하루에 콘텐츠 하나당 한 번만 센다
- 생년월일도 이름도 안 담는다. 어느 콘텐츠가 좋았나만 알면 된다
- 실패해도 그분에게 안 알린다 — 우리가 알고 싶어서 물은 것이다

지킴이: [test/ask-why-they-leave.test.mjs](../test/ask-why-they-leave.test.mjs)

## 4. 다음에 볼 것

3주쯤 뒤에 이 세 줄을 다시 뽑는다. 짐작하지 말고 이걸 보고 정한다.

```sql
-- 다시 오는 사람이 늘었나 (지금 12%)
SELECT CASE WHEN date(created_at,'unixepoch','+9 hours')=date(last_login_at,'unixepoch','+9 hours')
            THEN '그날 하루만' ELSE '다른 날 또 옴' END AS k, COUNT(*) FROM mini_users GROUP BY k;

-- 도장이 얼마나 이어지나
SELECT user_key, COUNT(*) FROM mini_payment_requests WHERE pkg='checkin' GROUP BY user_key;

-- 무엇이 좋았고 무엇이 아니었나
SELECT feature, SUM(helpful) AS 좋다, COUNT(*)-SUM(helpful) AS 아니다 FROM mini_feedback GROUP BY feature;
```

⚠️ 이 셋이 그대로면 **문제는 되부르는 장치가 아니라 콘텐츠 자체**다. 그때는
기능을 더 만들지 말고 ④ 의 답을 읽고 잘 안 되는 것부터 덜어낸다.
